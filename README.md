`@sasjs/cli` is a Command-Line Interface to assist with creating, building, and deploying Data Science projects and HTML5 Web Applications on the SAS platform (both SAS 9 and Viya). Features include:

- Scaffold a new SAS App in seconds (`sasjs create myApp -t jobs`)
- Compile / Build SAS Jobs, Services & Macros _locally_ and deploy / execute _remotely_, in isolation from other developers (`sasjs cbd`)
- Build and deploy without recompiling - for when the services on disk are already the ones you want to ship (`sasjs bd`)
- Compile a single Job, Service or Test without touching the rest of the build (`sasjs compile identify --source sasjs/jobs/daily/load.sas`)
- Write the test coverage report to `sasjsbuild/coverage.json` on every compile, ready for a CI job to publish
- No dependency on the server filesystem
- Optionally synchronise a local folder onto the server filesystem using `sasjs fs`
- Trigger Viya Jobs & Flows (`sasjs job execute` / `sasjs flow execute`)
- Enforce code quality rules with `sasjs lint`
- Check what SAS actually printed, and fail a pipeline on it, with `sasjs logcheck` - the same check reports the log of `run`, `request`, `job execute` and `flow execute`, and can fail those commands too via `logCheck.autoCheck`
- Generate HTML5 documentation (requires doxygen) with `sasjs doc`
- Create and execute SAS tests (`sasjs test`)

There is also a feature to let you deploy a frontend application as a set of streaming web services, bypassing the need to deploy to the SAS Web Server.

## Installation

1. Install globally using `npm` as follows:

```
  npm i -g @sasjs/cli
```

You can also use the tool without deploying through NPX as follows:

```
npx @sasjs/cli <command>
```

### Mock site app readiness

The host generated by `sasjs build mock` sets `window.__sasjsMockReady` synchronously before application scripts run. The promise resolves when the service worker, persistence and API bridge are ready; it rejects if startup fails or times out. The property is absent on normal, non-mock hosting.

This is a **breaking change** from the previous mock host, which delayed application scripts until the host was ready. Update each app before upgrading the CLI used to build its mock site: render immediately, but await the optional promise before every mock API request. If it rejects, show an error asking the user to refresh instead of making the request. For example, using app-specific rendering and loading functions:

```js
renderApp()

async function startApp() {
  try {
    const result = await window.__sasjsMockReady // absent outside the mock host
    const failure =
      result?.error || result?.driveError || result?.boot?.driveError
    if (failure) throw new Error(String(failure)) // older mock hosts may resolve errors
  } catch (error) {
    showStartupError('Mock site failed to start. Please refresh the page.')
    return
  }

  await loadInitialData() // makes a mock API request
}

startApp().catch(showLoadError)
```

Apply the same readiness gate to other request paths, not just initial loading. Application scripts now follow the browser's normal lifecycle; the host does not synthesize or redispatch `DOMContentLoaded` or `load` events.

### Mock site uploaded files

**Breaking change:** JavaScript mock services now receive `_WEBIN_FILEREF1`, `_WEBIN_FILEREF2`, etc. as session-local file paths, not decoded contents. Read bytes with `fs.readFileSync(_WEBIN_FILEREF1)` or text with `fs.readFileSync(_WEBIN_FILEREF1, 'utf8')`; do not stringify the path as if it were the file. `_WEBIN_NAME1` is the multipart field name and `_WEBIN_FILENAME1` the original filename. The unsuffixed names alias the first upload when present; `_WEBIN_FILE_COUNT` is zero without uploads. Uploads and derived files inside the per-request upload staging directory are transient; files a service writes elsewhere remain persistent. The browser mock supplies `fs` automatically: a top-level `const fs = require('fs')` currently collides with the host prelude and must be omitted. `webout('FETCH')` reads the current staged file lazily and decodes adapter CSV; it is not a binary interface. UTF-8 reads preserve a BOM, as in Node. The browser host limits each upload to 10 MiB and keeps its data in memory, including base64 conversion for bridged XHR. **`fs.createReadStream` and asynchronous service execution are not supported in the browser mock**: services are executed synchronously and uploads are removed when the service returns. Use synchronous reads in mock services; Server stream-based services require a separate browser-compatible implementation.

### Mock site SAS formatting

The mock code-format API uses the browser SAS language formatter. Every generated mock site includes the complete language vocabulary, even if formatting is never called, so it can serve DATA and PROC formatting without an external service. With `@sasjs/sas-language` 0.7.2, the `data` and `pubsdata` files add approximately 22 MB (21 MiB) uncompressed per site; the size can change with the language package version. The worker fetches vocabulary on demand, and reports an error if a required file is missing.

## Notes

Running `npm i -g @sasjs/cli@latest` does not always upgrade properly. This is due to a known bug in npm, which is fixed in npm 7.

If you are running NPM in version 6 or below, you can try running `npm update -g @sasjs/cli` instead, or - the sledgehammer approach - delete the files from the NPM folder and then do a fresh install.
